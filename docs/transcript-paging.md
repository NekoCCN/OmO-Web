# Web transcript paging

`GET /api/sessions/:id` returns the projected session and interaction state, the newest transcript rows, and (when a capture is available) `page: { id, olderCursor? }`. The response is at most 256 KiB of UTF-8 JSON and 40 messages; both limits include the newest page. If the state and required response fields cannot fit, the server returns `502 snapshot_state_too_large` instead of dropping pending interactions.

- `GET /api/sessions/:id/transcript?cursor=…` returns `{ messages, page, transcript? }`. Messages in each page are chronological. Prepend a page only to the matching `page.id`. No `olderCursor` means no older rows remain **in this capture**.
- `GET /api/sessions/:id/transcript/content?cursor=…` redeems an optional `message.historyContent.cursor` for `{ text, nextCursor? }`, at most 64 KiB of UTF-8 JSON per call. Start the expansion from the first chunk; do not append it to the preview. Append only subsequent chunks for that exact message and generation.
- `transcript.status: "truncated"` means the Native reader, projection, or capture limits omitted data; it does not mean that another page exists. `"unavailable"` means a local Native read limit withheld the entire transcript while preserving state. Malformed or refused Native receipts do not publish a capture.

The server stages the authorized live Native `get_messages` response once per capture, not a journal or `get_snapshot` reconstruction. Concurrent initial reads for the same binding can share the capture. Older pages and content never request `get_messages`. Page and content cursors are distinct authenticated capabilities: they expire with their generation and cannot be used for another session or at the other endpoint. Refreshing the initial snapshot publishes a new generation. Close, release, native source or engine replacement, compaction, and tree-navigation attempts invalidate the prior generation. Ordinary appends on the same live branch do not make a captured generation stale by themselves. Discard a cursor on `409` and do not automatically repeat an action.

The service uses a private, randomly named scratch directory under the host temporary directory per capture, with one private file. It retains at most four files (including at most two concurrent staging files), 60 MiB and 8,192 indexed messages per capture, and a five-minute lifetime. When space runs out, it retains the newest whole rows and reports omissions. Failed or abandoned attempts, expired and evicted captures, and normal service shutdown remove scratch files. Forced termination is not a normal shutdown; host temporary-directory cleanup applies to any files left then.
